# 专业发货单生成专家

从合同PDF或图片的OCR结果中提取关键信息，生成符合"装箱清单版式"标准的Word发货单。

> **版式沿革**：2026-08-27 起，发货单标准由"专业排版V2版"（蓝色7列表格）更新为"装箱清单版式"（黑色5列表格，仿产品装箱清单），以后一律按新版式生成。旧脚本 `generate_delivery_note.py` 仅作历史保留，不再使用。

## 触发条件

当用户请求以下任务时触发此技能：
- 将合同转换为发货单/送货单
- 根据合同生成发货单
- 从合同PDF提取信息制作发货单
- 上传合同并要求生成Word发货单
- 直接上传合同文件（PDF/图片）并要求处理

## 核心任务

1. **信息提取**：从OCR结果中提取需方（客户名称）、物料清单、合同编号等关键信息
2. **排版生成**：按"装箱清单版式"标准生成Word发货单，确保字体、字号、间距和表格样式统一
3. **业务校验**：校验提取信息是否符合业务规则（如发货单位正确、物料备注栏不为空等）

## 执行工作流

### Step 0：信息来源与识别方式

根据用户上传的文件类型，选择最优识别路径：

| 文件类型 | 识别方式 | 说明 |
|----------|----------|------|
| **PDF** | 1. 先用 `PyMuPDF (fitz)` 将每页渲染为高清图片（建议 1.5x~2x 缩放，保证文字清晰）；<br>2. 再使用 **Kimi 视觉模型**逐页读取图片并提取文字和表格内容。 | 严禁默认使用本地 PaddleOCR / pytesseract 等低精度 OCR 工具作为首选方案。 |
| **图片** | 直接使用 **Kimi 视觉模型**读取原图。 | 若图片模糊或文字过小，可提示用户重新截图或调高分辨率。 |

**核心原则**：视觉模型识别中文表格及复杂排版的准确度远高于传统 OCR 代码方案，尤其是包含多行数字、竖排文字或嵌套单元格的合同表格。

### Step 1：信息提取

从视觉模型识别的结果（或用户提供的OCR结果）中提取以下字段：

#### 1. 合同编号
- **优先从合同内容提取**：查找"合同号"或"合同编号"后的内容
- **次选从文件名提取**：若合同内容中无合同号，从PDF/图片文件名中提取10位以上数字串（只提取数字）
- 若仍无，显示"无"

#### 2. 需方（客户名称）
- 提取"需方:"或"收货单位:"或"买受方/买受人"后的内容
- 若无，显示"无法识别"

#### 3. 供方（发货单位，即页首公司名称）
- 提取"供方:"或"出卖方/出卖人"或"发货单位:"后的内容
- **必须校验**：若非以下三家之一，报错"错误的发货单位"：
  - 北京国华技术有限公司
  - 北京国华科技集团有限公司
  - 南通厚普机械科技有限公司

#### 4. 物料清单
- **优先从HTML表格提取**：若OCR结果含 `<tr>`、`<td>`，按表格结构提取
- **次选从纯文本提取**：按"序号 物料编码 物料名称 数量"模式提取，分离规格型号、单价、金额（价格信息仅用于核对，不写入发货单）
- **关键字段**：
  - 物料编号（来源于合同的编码/批处理号列；这不是规格，如无此内容，则显示"无"）
    - **重要复核**：若合同表格中的编码单元格采用垂直/多行排列（如第一行 `81463`、第二行 `10000`、第三行 `25`），**必须将多行数字全部提取并原样保留**，不可仅取第一行。
  - 产品名称
  - 规格型号（如和名称连在一起，则从名称中分离）
  - 数量（仅数字，不含单位；新版式无"单位"列）
  - 备注（来源于表格末尾列或特定标识，如"使用部门""货位""位号"，若原合同为空则填"-"）
- **必填校验**：每条物料"备注"栏不能为空（填"-"即可），否则报错

> 新版式**不再提取**交货地点、收货人、联系电话、地址（发货单中不含这些信息）。

### Step 2：业务逻辑校验

生成发货单前必须校验：

| 校验项 | 规则 | 错误处理 |
|--------|------|----------|
| 发货单位 | 必须为预设三家公司之一 | 报错："错误的发货单位" |
| 物料备注 | 每条物料的"备注"栏不能为空（"-"允许） | 报错："物料备注不能为空" |
| 表格列数 | 输出表格必须为5列 | 报错："表格列数不符合规范" |

**重要**：若校验不通过，**不生成不完整文档**，需清晰报告错误信息。

### Step 3：生成Word发货单（装箱清单版式）

#### 字体与字号
- 中文字体：微软雅黑；标题字体：黑体
- 英文/数字字体：Arial
- 字号：
  - 一级标题（发 货 单）：18pt 加粗居中
  - 页首公司名称（发货单位）：16pt 加粗居中
  - 右上角合同编号：10.5pt，右对齐
  - 表格内容：10.5pt（表头加粗）
  - 温馨提示：10.5pt（"温馨提示："标签加粗）

#### 段落与布局
- 行距：1.5倍
- 页边距：上/下 2.54cm，左/右 2.5cm
- 表格单元格边距：0.1cm

#### 表格样式
- 边框：所有边框（含内部）为0.5pt单实线，**黑色**
- **无任何底色**（不使用蓝/黄背景）
- 列结构：5列，分别为"产品名称"、"规格型号"、"数量"、"物料编号"、"备注"
- 首行为"客户名称"行：第1列为标签"客户名称"，后4列合并填入需方公司全名（加粗居中）
- 合计行：前2列合并为"合计"（加粗），数量列显示总数（加粗），后2列合并留空
- **重要**：表格中不得包含任何价格信息（单价、金额、总价等）
- **重要**：不得包含电话、地址、二维码

#### 文档结构

```
【右上角】合同编号：XXXX（右对齐，无二维码）

【页首公司名称】发货单位公司全名（居中，16pt，黑体，加粗）
【标题】发 货 单（居中，18pt，黑体，加粗）

【物料表格】
| 客户名称 | [需方公司全名，跨4列合并]                            |
|----------|----------|----------|------------|----------|
| 产品名称 | 规格型号 | 数量     | 物料编号   | 备注     |
| ...      | ...      | ...      | ...        | ...      |
| 合计（前2列合并）|   XX   | （后2列合并留空）              |

【温馨提示】
温馨提示：
1. 尊敬的用户，在您收到设备后先检查包装是否完好，如有损坏请按装箱单查点配件，无误后方可在托运单上签字接收。
2. 如查点实物与装箱单不符合，请立即和我公司联系，以便为您提供及时周到的服务。
```

### Step 4：代码实现要点

- 使用 `run` 级别设置中英文字体，确保混排正确
- 通过 `OxmlElement` 精细控制表格边框、单元格合并、单元格边距等高级样式
- **文件名格式**：`{日期}_发货单_{收货单位核心名称}.docx`，日期格式为6位数字（如260827），置于最前方
- 日期生成格式：`datetime.now().strftime('%y%m%d')`
- **收货单位核心名称提取规则**：
  1. 去除开头的省市名（如"北京"、"上海"、"江苏省"、"内蒙古"、"广东省"等）
  2. 去除结尾的"有限公司"、"有限责任公司"、"股份公司"等后缀
  3. 保留核心名称部分
  4. 示例：
     - "上海电气集团股份有限公司" → "电气集团"
     - "内蒙古巴山淀粉有限公司" → "巴山淀粉"
     - "北京国华技术有限公司" → "国华技术"
- 严格遵循排版规范，杜绝字体、颜色、间距不一致问题

## 错误处理与默认值

| 场景 | 处理方式 |
|------|----------|
| OCR失败 | 清晰报告错误信息，不生成文档 |
| 信息提取不完整 | 缺失字段按用户偏好留空或填默认值（"无"/"-"），生成后告知用户，不中断询问 |
| 校验不通过 | 报告具体校验错误，不生成文档 |
| 无法提取信息 | 使用预设默认值（如"无法识别""无"），并明确告知用户 |

## 输出格式

- **格式**：Word文档（.docx）
- **文件名**：`{日期}_发货单_{收货单位核心名称}.docx`
  - 日期格式：6位数字（年月日），如260827
  - 日期位置：文件名最前方
  - 收货单位核心名称：去除省市前缀和公司后缀后的核心名称
- **内容**：符合"装箱清单版式"标准的完整发货单，或详细的错误报告
- **桌面副本**：生成后按项目规范复制一份同名文件到 `C:/Users/yesli/Desktop`

### 优化执行流程（三步走）

```
Step 1: bash — 渲染PDF为图片（PyMuPDF 2x缩放，一步完成；图片合同直接用视觉模型读原图）
Step 2: 视觉模型/explore子代理 — 一次性精确读取表格全部内容（一步完成，避免来回确认）
Step 3: bash — 改数据参数后直接跑 generate_delivery_note_pl.py（一步完成）
```

**关键约束**：
- 视觉识别的提示词必须一次说清"把表格每个单元格的数字和文字都读完整"
- 避免因"没看清"而反复派子代理，如有模糊区域一次性要求仔细辨认（可对局部区域放大复核）
- 脚本复用优先，修改数据不超过3处时用 Edit 而非重写
